# What is *not* in the repo

CodeBreaker tracks **tool code only.** Input corpora, period Microsoft toolchains, VM images,
build artifacts, machine-specific config, third-party binaries, and any secrets are **never
committed** — they are attached locally and stay out of version control. This is deliberate:
the repo must ship clean as a *standard of measure*, carrying no proprietary or generated
payload. This document is the authoritative inventory of everything that lives on disk but is
not pushed, why, and how to re-attach it on a fresh clone.

## The ignore layers

Three `.gitignore` files enforce this, innermost-wins:

| File | Scope |
|---|---|
| `.gitignore` | repo root — data home, caches, build output, local config, user inputs |
| `engine/xbox/.gitignore` | the Xbox 360 subsystem — samples, console secrets, vendored/third-party tools |
| `tools/nasm-masm/.gitignore` | the vendored assembler — built `nasm`/`*.exe`/`*.o` output |

A fresh clone plus `pip install -r requirements.txt` plus a filled-in `config.json` is a
complete, working tool. Everything below is additive.

## 1. `binaries/` — the data home (≈ 28 GB, git-ignored in full)

The single home for all bulk data. Attach your own; nothing here is distributed.

| Path | Size | What it is | Re-attach |
|---|---:|---|---|
| `binaries/vms/` | ~18 GB | VMware VM images (incl. the pristine Win95 boot VMDK) | supply your own VM; boot in VMware |
| `binaries/win95/` | ~4.2 GB | Win95 input corpus + disassembly/work (`msc6_data`) | point `config.json:msc6_data` |
| `binaries/toolchains/` | ~4.1 GB | period MS toolchains + DOSBox-X (`msc6_toolchain`, `dosbox_x`) | install + point `config.json` |
| `binaries/media/` | ~1.2 GB | reference media / captures | optional |
| `binaries/work/` | ~603 MB | build + trace scratch (regenerable) | regenerated by the pipeline |
| `binaries/latticec/` | ~119 KB | the MS C 2.03 inverse **oracle** (`msc203_oracle`) | point `config.json:msc203_oracle` |
| `binaries/ledger/` | ~100 KB | generated coverage/verification ledgers | regenerated by the tools |
| `binaries/docs/` | ~52 KB | working notes / data-side docs | — |

> The MS C 2.03 oracle in `binaries/latticec/oracle16/` (MC1.EXE / MC2.EXE) is what the
> `wt inverse` engine gates against. It is small but essential to that subsystem; the rest of
> the Lattice C project was integrated into the engine and its raw folder deleted.

## 2. Local configuration (git-ignored)

| Path | What it is | Re-attach |
|---|---|---|
| `config.json` | machine-specific external-tool paths | `cp config.json.example config.json`, fill in |

`config.json.example` **is** tracked and documents every key: `dosbox_x`, `msc6_toolchain`,
`msc6_data`, `msc203_oracle`, `nasm`, `masm`, `msvc152c`, `sevenzip`, `ghidra`. Paths may also
be supplied through the environment (`env.sh`: `WT_DATA_ROOT`, `WT_WIN95_ROOT`,
`WT_<ERA>_DATA`).

## 3. Third-party toolchain binaries (never distributed)

License and provenance keep these out; you install/build them yourself.

| Path | Size | What it is |
|---|---:|---|
| `binaries/toolchains/…` (DOSBox-X, DOS-era MS C/MASM/LINK) | (in §1) | period build toolchain — attach your own |
| `engine/xbox/xbt/crypto/bin/*.exe` | ~2.6 MB | PowerPC toolchain (`xenon-as.exe`, `xenon-objcopy.exe`) for the Xbox path |
| `engine/xbox/xbt/vendor/` | ~31 MB | third-party libraries vendored on disk for the Xbox subsystem |
| `tools/nasm-masm/nasm.exe` (+ `*.o`) | ~11 MB | the **built** nasm-masm assembler — *source is tracked, binary is not* |

> `tools/nasm-masm/` ships as **source**. Build it (`sh autogen.sh && ./configure && make`, or
> `nmake -f Mkfiles/msvc.mak`) and point `config.json:nasm` at the resulting executable to
> enable the native assembler backbone.

## 4. Console secrets & copyrighted samples (excluded by policy)

**Never committed under any circumstance.** Secrets are excluded on principle; samples are
excluded on both regenerability and copyright grounds.

| Path | Size | What it is |
|---|---:|---|
| `engine/xbox/NexGen_Review/` | ~21 MB | Xbox console research material incl. device secrets — **kept strictly local** |
| `engine/xbox/samples/` | — | copyrighted game assets / regenerable sample data (`samples/README.md` is tracked) |
| `engine/xbox/files/` | — | user-dropped title binaries (copyrighted) |

## 5. Build artifacts, caches & generated data (regenerable)

| Pattern | What it is |
|---|---|
| `__pycache__/`, `*.pyc` | Python bytecode caches |
| `build/`, `dist/`, `*.manifest`, `*.spec` output | PyInstaller packaging output |
| `reports/` | generated coverage ledgers, conduct/*.json, logs |
| `*.o`, `*.obj` | object files (recompile95 / assembler build output) |
| `engine/diff/*.db`, `*.db-wal`, `*.db-shm` | the Transpiler-Diff corpus database (rebuild via `wt diff ingest`) |
| `reference/`, `files/`, `*.iso` | user-supplied reference trees / inputs / disc images |

## Re-attaching on a fresh clone — checklist

1. `pip install -r requirements.txt`
2. `cp config.json.example config.json` and fill in the paths you use.
3. Attach `binaries/` (corpus, toolchains, VMs) and point `config.json` / env vars at it.
4. (Optional) build `tools/nasm-masm` and set `config.json:nasm` for the native assembler.
5. `python wt.py doctor` — confirms what is and isn't configured.
