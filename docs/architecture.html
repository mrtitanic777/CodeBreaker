CodeBreaker Architecture

CodeBreaker takes a compiled program apart, writes source for it, builds that source, runs the rebuild beside the original in an emulator on the same inputs, and records what it saw. A function counts as reconstructed only when the two behave alike.

Theory of operation

The goal is readable, maintainable source in the language the program was first written in, which compiles and behaves as the original did. Getting the same bytes back is a useful hint about which of several working sources is closest to what a person wrote. It is never the goal.

Everything follows from one rule: nothing is believed until it has been observed. Every function goes through the same five steps: decompile, build, run both, compare, record. The machinery around those steps (caching, signatures, worker pools, the judge's own test) exists to make the loop cheap enough to run over hundreds of thousands of functions, and strict enough that a pass means something.

One path, many platforms

A platform is a descriptor in platforms/: its processor (the decompiler's language id), container, source language, lane module and runner. Its lane, verify/<kind>.py, provides four functions: profile, prepare, build, judge. reconstruct.run never branches on platform. Adding a platform means adding one descriptor and one lane file.

The decompiler knows processors, not files

describe.py does the loader's work: it lays NE segments out at selectors, applies relocations and turns imports into far pointers. It also records facts read from the binary instead of guessed, such as function starts and ret N byte counts (which fix the calling convention). The native decompiler.exe, a forked Ghidra decompiler core driven by SLEIGH languages, turns that description into C.

C that compiles and means the same

c_text.py turns the decompiler's output into C that OpenWatcom accepts. It defines base types, binds globals to the original's addresses, declares every function and import with its real convention, and keeps address-taken locals in the frame. struct_text.py writes field accesses as fields.

Judged by behaviour

Both sides run in an emulator on the same inputs. Each run is reduced to a fingerprint: how it ended, what it returned, which calls it made and with which arguments, what memory it wrote, the stack and the saved registers. The first difference decides the verdict. Inputs are aimed at branches no earlier input reached.

Never the same work twice

Compiles and decompiles are cached under a hash of everything they depend on, including the tool itself. A verdict carries a signature built from the function's text, the header and its callees' signatures. If a source edit leaves the compiled code unchanged, the verdict is kept and nothing is re-run.

One store of truth

state/functions.sqlite holds every module, function, candidate source and verdict. Verdicts are filed per verifier profile, so changing the judge adds new verdicts beside the old ones instead of erasing them. Every report reads from the store: scoreboards, module files, the web console and the MCP tools.

Crashes are data

jobs/pool.py spreads judging over worker processes at low priority. When emulated native code kills a worker, the items it was running are retried one at a time. The one that crashes again is recorded as inconclusive, and no item is lost.

The judge is judged

verify/teeth.py deliberately breaks functions the judge passed and counts how many breaks it catches. The project once found its earlier verifier passing 41% of broken bodies. Since then, every “verified” figure carries the measured strength of the check behind it.

Platforms and lanes

Platforms are tried in this order: java, xbox360, xbox, nes, sms, gb, genesis, zx, msx, win32, win16, vxd, dos. The first one that recognises a file decides its lane. Specific formats come before general ones, because a .xex or a ROM would otherwise be mistaken for a plain executable.

The core of the system is small. Orchestration, the store, the pool and the platform registry together come to under 1,100 lines. Most of the code is per-format and per-toolchain knowledge, which is where it belongs.

Findings from this read

What a fresh pass over the code shows: what holds up, and where the code and its documentation have drifted apart.

  • Strong
    The spine is truly single. reconstruct.run has no platform branches, and 13 platforms plug in through four functions each. This is the main reason the tool could grow from Win95 to consoles, Java and XNA without forking.
  • Strong
    Incremental work is sound. Signatures over call-graph cycles, plus the object-code digest, mean a verdict is reused only when what was judged truly didn't change. The rule is stricter than per-file caching and cheaper than re-judging.
  • Strong
    Failure is first-class. no-synth, no-compile, inconclusive and stub-callee are all recorded with reasons, so the store can explain every function instead of only counting successes.
  • Drift
    docs/architecture.png shows five kinds of code. platforms/ now has thirteen, and the picture leaves out Java, XNA, the consoles and recompile.
  • Shape
    invert/omf.py is a second, standalone OMF parser. exact/omf.py was already folded into formats/omf.py as “one OMF-86 reader for exact, invert and the builders”, so invert's copy looks like an unfinished merge.
  • Measured
    The judge catches 80% of small wrong changes. teeth over 13 modules (2026-10-27): VERIFIED caught 800 of 1,005 breaks, VERIFIED (weak) 175 of 261. Stores left out and operators changed are caught least (56%, 58%); two thirds of the survivors were in code that fully ran (docs/STATUS.md).
