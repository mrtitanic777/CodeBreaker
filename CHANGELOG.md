# Changelog

What changed in each release of CodeBreaker. Newest first; [docs/RELEASING.md](docs/RELEASING.md) says how a
release is made. Each entry lists what a user notices: new commands and lanes, fixes, changes in behaviour.

## Unreleased

### Added
- The universal translator, phase 2 (roadmap track 4): the C# front end and the C++17 back end now carry iterators (`yield return` / `yield break`, as a stackful coroutine in `cs::Coroutine`), async/await (`Task`, `Task<T>`, `Task.Delay/Yield/Run/WhenAll/FromResult`, `async Task Main`, on a scheduler with a virtual clock), switch statements over patterns and `when` guards, `var` patterns, query expressions with `let`, `join`, `group by` and several `from` (the compiler's anonymous types become generated classes), and nullable arithmetic (lifted operators, unary minus, `+=`, `??` chains, `.Value` throwing `InvalidOperationException`, `GetValueOrDefault(d)`). LINQ in csrt.hpp is now lazy as .NET's is (generators and endless sources work). New L2 nodes `YieldReturn`, `YieldBreak`, `Await`; the C# back end writes them too (a second back end out of the same L2: the features round-trip to equivalent C#). `codebreaker judge-cs-cpp` on the 23 programs: all agree with g++, clang and MSVC. Fixed: `(a || b) && c` was written without its parentheses. The Python front end lowers generator functions too (`yield` to `YieldReturn`, a `py::generate` coroutine in the C++17 output), and the new `codebreaker judge-py-cpp` judges Python modules against CPython: its corpus agrees on g++, clang and MSVC. See docs/TRANSLATOR_DESIGN.md, "Phase 2 as built".
- Xbox 360 recompiled titles, round 4: `recompile-project` translates every PowerPC module a title ships (Terraria's `HostLoader.dll`, `RuntimeHost.xex`, `NetCFUserMode.dll`; Left 4 Dead 2's 21 engine DLLs; Forza 4's `XMediaFacade` and `SpeechFacade`) with its own configuration and symbol suffix and links it; `XexLoadImage` loads a module by name, binds its imports to other modules' exports and runs its entry. Exports are function roots of the recompiler, and an executable section counts as code. Also the 10-bit front buffer, `k_16_16_FLOAT` textures, `NtSignalAndWaitForSingleObjectEx`, exports found by ordinal name, named kernel objects opened by name (Top Spin 2 runs: 1 to 6000 frames), the XNA game-services event, an end to the relaunch loop of a title that cannot start, and the GPU harness (`CB_SHADER_TEST`) with Texture3D volumes and the new formats.
- The PlayStation 4, PlayStation 5 and Xbox One / Series lanes (x86-64, roadmap track 9): `info` and `reach` take an x86-64 ELF a payload SDK or OpenOrbis links (a PlayStation program is one that names the system's libraries; the console is told by the file name, since a payload does not say), OpenOrbis's fake SELF `eboot.bin` (read back into the ELF it holds; imports by NID, named by hashing a list of well-known function names), and the PE32+ of a dev-mode UWP app in its `.appx` / `.msix` / `.msixbundle` package (zip64 included) or loose. A `.pkg`, a PS5 SELF, a retail-typed SELF and an encrypted `.xvc` / `.msixvc` / `.eappx` are recognised and refused. There is no second x86 core: the decoder is Capstone's 64-bit mode, the runner Unicorn's x86-64 engine and the assembler NASM; the new `source/x64_writer` writes a whole file as one NASM source (a section per run with `vstart`, `[rel label]` for rip-relative operands, `mov_`-style macros for the register moves NASM encodes the other way, strings and `times` runs as data, the rest found out in rounds) and rebuilds it byte for byte. Functions come from the entry, symbols, initialisers, relocation pointers and an exception directory; imports are `got_<name>` / `__imp_<name>` slots and a PLT stub is named for its import (`call puts`). `reach --judge` runs each function on Unicorn with relocations applied and each import a stub that logs `name(args)`, `syscall` logged by FreeBSD name. Real open-source homebrew, all rebuilt identical and verified: OpenOrbis's hello_world and graphics (GPL-3.0; the ELF and the eboot.bin made by its own create-fself), ps5-payload-dev's ftpsrv, klogsrv and elfldr (GPL-3.0; PS4 and PS5 builds), and Moonlight UWP's x64 package (GPL-3.0; the 3.2 MB app executable, 8,771 functions, and one of its DLLs). Details and numbers in docs/TESTED_SOFTWARE.md and docs/LANES.md.
- The Nintendo Switch lane and the AArch64 core (roadmap track 9): `info` and `reach` take a homebrew `.nro` (header, segments, MOD0, the dynamic R_AARCH64_RELATIVE relocations, the asset section kept as data), a `.nso` (LZ4 segments inflated: the rebuilt file is the decompressed program) and the AArch64 ELF devkitA64 links; an NSP, XCI or NCA is recognised and refused. The A64 core is CodeBreaker's own: one table of about 1,000 rows (`decompile/a64`, with `a64_table` and `a64_simd`) that the decoder, the text and the assembler (`build/a64_asm`, GNU as syntax with `:lo12:`, `.incbin`) read, so every decodable word assembles back to itself (60 million random words in the test, and about 98% agreement with Capstone's text), covering the integer groups, every load and store form (pairs, exclusive, ordered), branches, system instructions, scalar floating point and the common Advanced SIMD forms. The interpreter (`emulate/a64`, `a64_simd`) runs them with flags, models the Horizon kernel (SVCs logged by name, IPC commands and `sm:` service names decoded, the homebrew loader ABI) and stops, with its reason, at what it cannot run. `source/switch_writer` writes GNU as source (address pairs as `adrp x0, D_x` / `:lo12:`, relocated words as labels, the relocation table, the header and MOD0 field by field) that rebuilds a NRO byte for byte; `codebreaker reach --judge` verifies all 956, 2,357 and 14,580 functions of ftpd-classic, ftpd and NX-Shell (docs/TESTED_SOFTWARE.md). Left: SVE/SME, the crypto extensions, LSE atomics, half-precision arithmetic (and `fcvtn` / `fcvtl` of half precision).
- The Neo Geo Pocket lane and the Toshiba TLCS-900/H core (roadmap track 9): `info` and `reach` take a `.ngp` / `.ngc` / `.npc` cartridge. The TLCS-900/H is one table (`decompile/tlcs900`: the first byte picks register, source-memory, destination-memory or single-byte rows, the second byte the operation; registers of every bank and part, all addressing modes) read by the disassembler, the assembler (`build/tlcs900_asm`, over `build/byte_asm`, whose new `converge` option sizes an absolute address by its value) and the interpreter (`emulate/tlcs900`: flags, register banks, mul / div, block moves; `swi` and the BIOS vector table are stubs logged by number). The writer (`source/ngp_writer`) writes the whole cartridge with the interrupt handlers a program stores into the BIOS vector table as functions and hardware registers by name; the K2GE register names follow NgpCraft's reference. ASTEROIDS (MIT) rebuilds identical and 60 functions verify.
- The PlayStation 3 lane (Cell PPU, roadmap track 9): `info` and `reach` take a PSL1GHT ELF (ELF64 big-endian PowerPC) or an unencrypted SELF (an encrypted one is recognised and refused); the program is written back as GNU as source (function descriptors found in the data, imports named from PSL1GHT's published NIDs, `sc` annotated with the lv2 system call) and rebuilt byte for byte, and `reach --judge` runs each function in the PowerPC interpreter the Xbox 360 and GameCube lanes share. `decompile/ppc` gained the 64-bit rows (LD, STD, the rotates, DIVD, MULLD, EXTSW, CNTLZD ...) behind a `wide` flag, so the GameCube, Wii and Wii U decoding is unchanged. No open-source PS3 homebrew with plain segments was found, so the lane is proved on ELF files the tests build
- The PlayStation Vita lane (Cortex-A9, ARMv7-A, roadmap track 9): `info` and `reach` take an unencrypted SELF (a `.vpk`'s `eboot.bin`, zlib-compressed segments inflated; an encrypted one is recognised and refused) or its ELF; the program is written back as GNU as Thumb source (imports named from VitaSDK's NID database, `bl sceCtrlPeekBufferPositive`) and rebuilt byte for byte, and `reach --judge` runs each function in the ARM interpreter (now with Thumb-2's branches, IT, CBZ, the common 32-bit integer instructions and the VFP). The 32-bit Thumb-2 instructions without an assembler encoding are written as `.word` with the disassembler's text as a comment
- The Nintendo 3DS lane (ARM11, roadmap track 9): `info` and `reach` take a homebrew `.3dsx` (header, relocation tables, segments) or the ARM ELF devkitARM links it from; the file is written back as GNU as source (pointer words as their target's label, kernel calls named: `@ svcSendSyncRequest`) and rebuilt byte for byte, and `reach --judge` runs each function in CodeBreaker's ARM interpreter (now with ARMv6K and the VFP) over the process's memory. Encrypted `.cia` / `.3ds` are recognised and refused. The ARM core gained `decompile/arm_ext`, a table of ARMv6 and VFP instructions read both ways
- The Vectrex lane and the Motorola 6809 core (roadmap track 9): `info` and `reach` take a `.vec` / `.bin` / `.gam` cartridge (the `g GCE` header read field by field, the program at the byte after it). The 6809 is a table, assembler (`build/m6809_asm`, with ORG, FCB, FDB, FCC, FILL, RMB and EQU) and interpreter of its own: every opcode of the three pages round-trips (disassembled text assembles to the same bytes, indexed forms and indirect ones included) and the interpreter runs them all (flags, MUL, DAA, EXG/TFR, PSH/PUL, every indexed mode). The program comes back as 6809 source with the BIOS routines (Wait_Recal, Moveto_d, Draw_VLc ...) and the VIA 6522 registers by name; the lane runs functions over the Vectrex's memory with the system ROM as stubs whose entries are logged. 4 open-source cartridges rebuild identical (docs/TESTED_SOFTWARE.md).
- The Virtual Boy lane and the NEC V810 core, and the Intellivision lane and the CP1610 core (roadmap track 9): `info` and `reach` take a `.vb` cartridge (header, vector slots, reset slot) and an Intellicart `.rom` / raw `.int` (segments, CRC-16, the header at $5000). The V810 is a table, assembler (`build/v810_asm`) and interpreter of its own: every bit pattern that decodes round-trips through the assembler, the interpreter runs all of it (flags, the 64-bit multiply, floating point, the bit-string instructions). The CP1610 likewise (10-bit decles, SDBD, every addressing mode; `build/cp1610_asm` writes the .rom with its CRCs). Programs come back as source with the VIP / VSU / hardware registers, and the STIC / PSG registers, by name; the lanes run functions over each machine's memory with every device access logged. 4 VUEngine demos (522 functions) and Space Versus (54) rebuild identical and verify (docs/TESTED_SOFTWARE.md).
- The Odyssey 2 lane (Intel 8048) and the Channel F lane (Fairchild F8), roadmap track 9: `info` and `reach` take a `.o2` cartridge (at $0400) and a `.chf` (or a `.bin` starting $55 $2B, at $0800). Each core is a table, assembler and interpreter of its own, every opcode round-tripping (`decompile/i8048`, `decompile/f8`, `emulate/i8048`, `emulate/f8`), over a shared directive layer (`build/byte_asm`: ORG, DB, DW, FILL, EQU, labels). The programs come back as source and rebuild identical; the lanes run functions with every port, data-space and BIOS access logged. Verified on hand-made cartridges only: no open-source homebrew was found for either.
- The Philips CD-i lane (68070, the 68000 core): `info` and `reach` take a disc image (`.iso` / `.bin` / `.cdi`, 2048-byte sectors, found by the Disc Label) or a CD-RTOS module file; the executable modules (OS-9/68000: header parity checked) come back as Motorola-syntax source with the header field by field, `TRAP #0` + call word written as the system call's name (F_Exit, I_Write ...), and a disc is rebuilt with the modules put back. The lane runs functions in the 68000 interpreter with every system call stubbed and logged. The filesystem (path table, directories) is not read.
- Four more console lanes (roadmap track 9): the Atari 5200 (6502: `info` and `reach` take a `.a52` or a raw `.bin` of 4, 8, 16 or 32 KB ending at $BFFF with the start address in its last two bytes; GTIA, ANTIC and POKEY registers named and logged, the BIOS window stubbed; dasm source), the Atari Jaguar (68000: `.j64` / `.jag` / `.rom` cartridges at $800000 and COFF executables `.cof` / `.abs`, Tom's and Jerry's registers named and logged, the GPU and DSP code kept as data; Motorola-syntax source), the Bandai WonderSwan and WonderSwan Color (NEC V30MZ: `.ws` / `.wsc`, the footer with the reset far jump, the I/O ports named and logged, run on Unicorn's 16-bit x86; NASM source found out in rounds against NASM) and the 3DO (ARM60, big-endian: an Opera disc `.iso`'s LaunchMe, or a bare AIF; the ARM interpreter gained `Bus::set_big_endian`; GNU as source, Madam and Clio registers named, the operating-system SWIs logged). `platforms::Id` gained `Atari5200`, `ThreeDo`, `Jaguar` and `WonderSwan`.
- The Sega Dreamcast lane (SuperH SH-4, roadmap track 9): `info` and `reach` take a Dreamcast disc: a GD-ROM dump's `.gdi` (the track files beside it; IP.BIN is in the last data track, whose volume is numbered from the start of the disc), a DiscJuggler `.cdi` (the boot track is found by its content: IP.BIN's ID at a sector start with an ISO 9660 volume 16 sectors on, in 2048, 2336 or 2352-byte sectors), or a plain `.iso` / raw `.bin`. IP.BIN's header is read field by field (hardware ID, maker, device information, areas, peripherals, product number, version, release date, boot file, software maker, title), the file it names (1ST_READ.BIN) is found and loaded at $8C010000 right behind IP.BIN's 32 KB, and a scrambled 1ST_READ.BIN (homebrew on a CD-R) is detected by what the scramble does to delay slots, descrambled, and scrambled again in the disc the lane rebuilds. The SH-4 is a variant of the SH-2 core (`decompile/sh2`, `build/sh_asm`, `emulate/sh2` + `emulate/sh4`): little-endian words, the FPU (single and double operations by FPSCR.PR, pair moves by SZ, FIPR, FTRV, FSCA, FSRRA, FMAC, FLOAT/FTRC, FCNVSD/FCNVDS, FSCHG, FRCHG), SHAD/SHLD, PREF/OCBI/OCBP/OCBWB/MOVCA.L/LDTLB, SSR/SPC/SGR/DBR and the banked registers, and every decodable word assembles back to itself. The interpreter runs register banks (SR.RB), RTE through SPC/SSR, SR.FD, the store queues (PREF flushes to the address QACR gives), and holds the P4 area's registers (cache, MMU, bus controller, DMAC, timers, serial ports) as logged state; the machine model (`engine/machine_dreamcast`) names and logs the Holly's system, Maple, G1/GD-ROM, G2 and PowerVR registers, the AICA and the tile accelerator's FIFOs, and stubs the BIOS's system calls (each entry logged). The disc comes back as GNU as source (IP.BIN's header field by field, physical addresses with the cache bits written `label + 0x80000000`, registers by name, little-endian data) that the lane's own assembler builds back byte for byte.
- The GameCube, Wii and Wii U lanes (PowerPC 750: Gekko, Broadway, Espresso): `info` and `reach` take a GameCube or Wii DOL (`.dol`), a PowerPC ELF (`.elf`) and a Wii U RPX / RPL (`.rpx`, `.rpl`; the compressed sections are inflated and the file laid out again), and tell the consoles apart by what the program touches (MEM2 and the Hollywood registers mean the Wii). The program comes back as GNU as source (the header field by field, each section at its load address, functions found by calls, prologues and pointers, an ELF's symbol names, hardware registers by name, `name@ha` / `name@l`) that CodeBreaker's own assembler builds back into the same file, byte for byte, and its functions are judged in the Xbox 360's PowerPC interpreter extended with Gekko's paired singles, the quantization registers and logged hardware registers. `decompile/ppc` is a table of every 750 instruction read both ways. Eleven open-source programs rebuild identical (docs/TESTED_SOFTWARE.md).
- `codebreaker` builds on Linux (roadmap track 8, phase 2): the service, the MCP server and the QEMU monitor client use `core/socket.hpp` (which gained send timeouts and `timed_out()`); the service's job processes and its detached launch use `core/process.hpp` (`Capture::ToFile(path, append)`, `ProcessSpec::terminal` for the Python terminal interface, `Process::pid()`, `start_detached`); the Xbox crypto takes random bytes, AES/DES/3DES and RSA keys and signatures from `core/crypto.hpp` (CNG on Windows, OpenSSL's libcrypto elsewhere); the allocator stays a Windows-only link-time choice. Windows behaviour is unchanged. docs/LINUX.md has the state.
- The Sega 32X and Sega Saturn lanes (SuperH SH-2, the first SuperH lanes): `info` and `reach` take a 32X cartridge (`.32x`; the Genesis ROM with the add-on's header at $3C0: the SH-2 program's ROM offset and length, the master and slave start addresses and vector bases) and a Saturn disc (`.iso` 2048-byte sectors, raw `.bin` 2352-byte sectors, or the `.cue` sheet naming one; IP.BIN's header, its four area-code entries and initial program, and the first program the root directory names, at the load address the header gives). The SH-2 is a decoder/disassembler table, a GNU as assembler (`build/sh_asm`: `.long` and `.word` big-endian, `.align n` as 2^n) and an interpreter of its own (`decompile/sh2`, `emulate/sh2`: every SH-1 and SH-2 instruction, delay slots, MAC.W/MAC.L with saturation, DIV0S/DIV0U/DIV1, the multiplies, the divide unit on the chip, a bus of RAM regions and logged devices). The programs come back as GNU as source: a PC-relative `mov.l @(disp,pc),rn` is followed to its constant, which is named (`K_<address>`, written by what it holds: a label of the program, a register of the machine such as `MARS_SYS_COMM0` or `SCU_IST`, a variable in RAM, a number), functions called only through a pointer are found from those constants and from the bytes that follow another function's end, and the header and the vector tables are written field by field. A 32X cartridge is two sources, the SH-2 program (`<stem>.sh2.s`) and the 68000 side (`<stem>.asm`, the Genesis writer's), and the lane runs each side in its own interpreter; a Saturn disc's system area and first program are one source with an `.org` per part. The genesis lane no longer takes a 32X cartridge. Registered through `engine/machine_sh2` (`register_sh2_lanes`), as the Nintendo DS and Neo Geo lanes are. The 32X cartridges and the Saturn disc images of open-source homebrew rebuild identical and are judged (docs/TESTED_SOFTWARE.md). Not done: Dreamcast (SH-4: the FPU, pair moves, FTRV/FIPR; `.cdi`/`.gdi`, 1ST_READ.BIN) is the next session's.
- The PlayStation 2 and PSP lanes (MIPS R5900 and Allegrex, roadmap track 9): `info` and `reach` take a PlayStation 2 Emotion Engine `.elf` (or an `.iso` whose SYSTEM.CNF BOOT2 program is one) and an unencrypted PSP program (`.elf`, `.prx`, `EBOOT.PBP`; an encrypted `~PSP` module is recorded as not handled). The MIPS decoder and assembler gained the R5900 (128-bit LQ/SQ, the multimedia instructions, the second multiplier, the EE FPU, VU0 moves and macro mode's first function group) and the Allegrex (CLZ MAX MADD EXT INS SEB WSBH ROTR, the VFPU's loads, stores and main arithmetic). The ELF is written whole as GNU as source (headers, sections, symbols, a PRX's relocations and a PBP's other files as data) and rebuilt byte for byte; PSP imports are named by NID from pspsdk's published lists. Functions run in one little-endian interpreter over each console's memory map with the hardware registers named and logged and the EE kernel's calls / the PSP's imports logged. Rebuild identical on open-source homebrew: three PlayStation 2 ELFs, nine PSP modules and three EBOOT.PBPs (docs/TESTED_SOFTWARE.md).
- The Nintendo 64 lane (MIPS R4300i): `info` and `reach` take a `.z64`, `.v64` or `.n64` ROM (the three byte orders read as one; the 64-byte header field by field, the boot code IPL3 as data with its CIC chip named, the header's checksums recomputed from the program and compared, the program at the entry point the boot code copies it to); the program comes back as GNU as source (every function, branch likely, doubleword and FPU instructions, hardware registers by name: MI_INTR_MASK, VI_ORIGIN, PI_STATUS ...) that CodeBreaker's own big-endian MIPS assembler builds back into the same ROM, byte for byte, in the byte order the file had, and its functions are judged in CodeBreaker's own R4300i interpreter (64-bit registers, the TLB, the FPU with its rounding modes and MIPS's NaNs, RDRAM, the cartridge with PI DMA, the RCP's registers logged; the RSP and the RDP are not run). The MIPS decoder, assembler and data directives take an R4300 variant, and the PlayStation's behaviour is as it was. 79 open-source N64 programs rebuild identical (docs/TESTED_SOFTWARE.md).
- The TurboGrafx-16 / PC Engine lane (HuC6280): `info` and `reach` take a `.pce` / `.tg16` HuCard (8 KB banks, with or without a 512-byte copier header). The HuC6280 is a table, assembler and interpreter of its own on the 65C02 core (the Rockwell bit instructions, the block transfers TII TDD TIN TIA TAI, TAM / TMA, ST0 ST1 ST2, SET, SAX SAY SXY, CSL / CSH, TST, BSR, and page zero and the stack at $2000 / $2100). The program comes back as ca65 source (`.setcpu "HuC6280"`) and an `ld65` configuration, one segment per bank: code is what flow reaches from the five vectors, with the eight mapping registers followed through `LDA #n; TAM #mask` so a jump into a page lands in the bank it is mapped to, the VDC / VCE / PSG / timer / joypad / interrupt registers carry their hardware names, zero-page operands are `zp_20`, and an instruction that would not assemble back into its bytes is written as data. CodeBreaker's own assembler builds it back into the same card, byte for byte, and each function is run beside the original's in the HuC6280 over the console's memory (MPR mapping, RAM, chips logged by register name, the VDC register ST0 selected shown) when the source is edited.
- The Super Nintendo lane (65C816): `info` and `reach` take a `.sfc` / `.smc` cartridge (a 512-byte copier header is stripped and kept; LoROM or HiROM found from the internal header at $7FC0 / $FFC0 by its checksum pair, map mode, title and vectors). The 65C816 is a table, assembler and interpreter of its own (all 256 opcodes; the accumulator and index registers 8 or 16 bits wide by REP / SEP / XCE; direct page, data and program banks, long, stack-relative and block-move forms; decimal ADC / SBC). The program comes back as ca65 source (`.p816`, `.a8` / `.a16` / `.i8` / `.i16` before an immediate whose width changes, the internal header field by field, PPU / APU-port / WRAM-port / CPU / DMA registers by name) and an `ld65` configuration, one segment per bank; the register widths and emulation mode are followed through the code from the reset vector, so each instruction is decoded at the length the path to it leaves. CodeBreaker's own assembler rebuilds the cartridge byte for byte, and each function is run beside the original's in the 65C816 over the console's memory (LoROM / HiROM map, 128 KB of RAM, the chips logged by name, DMA run and HDMA logged) in the widths it starts in. The SPC700 sound program stays data.
- The 65xx assembler (`build/m6502_asm`) understands the 65C816's `.a8` / `.a16` / `.i8` / `.i16` and takes the encoder's branches that are not two bytes (the HuC6280's BBRn / BBSn, the 65C816's BRL and PER); the 6502 interpreter can move page zero and the stack (the HuC6280's are at $2000 / $2100).
- The Nintendo DS lane (ARM946E-S + ARM7TDMI): `info` and `reach` take a `.nds` ROM; both programs come back in one GNU as source (`.cpu arm946e-s` and `.cpu arm7tdmi` parts, ARM and Thumb state, literal pools under labels, hardware registers by libnds name), with the header field by field, the file name table, the file allocation table (a `.word file_N, file_N_end` pair per file, the files named from the FNT), the overlay tables and the banner (icon and UTF-16 titles) as data, and CodeBreaker's own assembler builds it back into the same ROM, byte for byte. The ARM decoder, assembler and interpreter gained the ARMv5TE additions behind an `Arch` parameter (BLX in both states, CLZ, QADD/QSUB/QDADD/QDSUB, SMLAxy and the other 16-bit multiplies, LDRD/STRD, PLD, BKPT, MCR/MRC; `.cpu` in the assembler picks the set), with the Game Boy Advance behaviour unchanged. The interpreter has the DS memory maps for each processor (main RAM, TCMs, shared and ARM7 WRAM, I/O, video memory) and coprocessor 15; functions are judged in the interpreter of their own processor. Open-source DS homebrew rebuilds identical (docs/TESTED_SOFTWARE.md).
- The Neo Geo and Sega CD lanes (68000): `info` and `reach` take a Neo Geo P-ROM (plain, with its words swapped, or a `.neo` container; two halves can be joined) and a Sega CD / Mega-CD disc image (`.iso` 2048-byte or raw `.bin` 2352-byte sectors; a Genesis probe no longer takes a disc for a cartridge). A Neo Geo program comes back as Motorola-syntax source: the vector table, the header at $100 field by field, the four callbacks the BIOS calls (`user`, `player_start`, `demo_end`, `coin_sound`), the security code, the vertical blank and raster handlers, the LSPC / system ports, the BIOS's calls (`SYSTEM_IO`, `FIX_CLEAR` ...) and variables by name, the second megabyte at the bank window; a `.neo` container's Z80 sound program (and a raw `.m1`) comes back as Z80 source beside it. A Sega CD disc's 32 KB system area comes back as one source holding the boot header, the main CPU's security code and IP (at $FF0000) and the sub CPU's SP (at $6000, entries from its jump table), the gate array and the CD BIOS's calls (`CDBIOS` ...) by name. CodeBreaker's own 68000 assembler builds each back byte for byte, and the functions are judged in the 68000 interpreter over each machine's memory map: the Neo Geo's work and palette RAM, system ports and memory card logged, the LSPC's video RAM modelled, the BIOS stubbed with each call logged; the Sega CD main CPU's Genesis map with the gate array and word RAM, the sub CPU's PRG-RAM, word RAM, PCM and gate array with each CD BIOS call logged. Open-source Neo Geo and Sega CD homebrew rebuilds identical (docs/TESTED_SOFTWARE.md). Not done: the Neo Geo's S / C / V ROMs, the Z80 sound program is not judged, code reached only through function pointers is not followed, Sega CD files after the system area (the programs the IP loads) are not read.
- The ColecoVision, SG-1000 / SC-3000 and Amstrad CPC lanes (Z80): `info` and `reach` take a ColecoVision `.col` cartridge (or a `.rom`/`.bin` with the `$AA55` header), an SG-1000 / SC-3000 `.sg` / `.sc` cartridge and an Amstrad CPC `.dsk` (standard and extended CPCEMU images: the AMSDOS directory is read and the best binary taken), `.sna` snapshot or AMSDOS `.bin`. Each program comes back as sjasmplus / pasmo source (WLA-DX for the SG-1000) with the machine's names (ColecoVision BIOS entry points, VDP and sound ports; the CPC firmware jumpblock) that CodeBreaker's own Z80 assembler builds back byte for byte, and its functions are judged in CodeBreaker's own Z80 with the machine's memory map: the firmware stubbed with each call logged by name, RAM where the machine has it, ports logged (the CPC's with all 16 bits), and no Sega mapper on an SG-1000. Open-source homebrew rebuilds identical (docs/TESTED_SOFTWARE.md).
- The Atari 2600 and Atari 7800 lanes (6502 family): `info` and `reach` take a raw 2600 cartridge (`.a26`; a bare `.bin` only if its reset code is plausible) of 2, 4, 8, 16 or 32 KB with the usual F8 / F6 / F4 bank switching, and a 7800 `.a78` (header versions 1 to 4; linear ROMs of 4 to 48 KB and SuperGame banks; the Activision, absolute, banked-RAM, POKEY and YM2151 boards and the 7800's 2600 mode are not modelled). The 6502 table, assembler (`dasm` syntax: `ORG` / `RORG` per bank, `.w` for an absolute zero-page form) and interpreter are shared with the NES lane; the interpreter's bus gained address masks (the 6507's 13 address lines), quiet RAM ranges and write-only ranges. Each program comes back as dasm source with the hardware's own names (TIA, RIOT, MARIA: `WSYNC`, `COLUBK`, `INTIM`, `BACKGRND`, `CTRL` ...; a TIA address is named by whether it is read or written) that CodeBreaker's own dasm-syntax assembler builds back byte for byte (the 7800's 128-byte header included), and its functions are judged in a model of each machine: the 2600's 128 bytes of RAM with the stack in its mirror, TIA and RIOT registers logged, bank switches logged as accesses; the 7800's 4 KB of RAM with its zero-page and stack windows, TIA, MARIA and RIOT logged, the SuperGame bank select logged. Open-source 2600 homebrew rebuilds identical (docs/TESTED_SOFTWARE.md); a 7800 jump from the fixed bank into a switchable bank is not followed (which bank is selected is a run-time fact), so SuperGame banks are mostly data.
- The Atari Lynx lane (65SC02): `info` and `reach` take a `.lnx` cartridge or a BS93 `.o` object (the homebrew loader format). The 65SC02 is a decoder table, assembler and interpreter of its own (BRA, STZ, TRB/TSB, PHX/PHY/PLX/PLY, INC A / DEC A, `(zp)` and `JMP (abs,X)`; BRK clears D; the indirect JMP does not wrap). A cartridge's boot ROM is modelled as "the loaded image": its encrypted first stage is decrypted (the published public key) and the loaders it starts are run, the ROM's shift routine and the cartridge register RCART0 played, to find which stretches of the cartridge are copied to which RAM, and where the loaders jump; those are the program, the rest of the file (the 64-byte header, the encrypted bytes, the directory, padding) is data. The program comes back as ca65 source with an `ld65` configuration, Suzy's and Mikey's registers by name (`SPRGO`, `DISPCTL`, `GREEN0` ...), that CodeBreaker's own assembler builds back into the same file byte for byte, and its functions are judged in the 65SC02 over the Lynx's memory (every Suzy / Mikey access logged). Open-source BLL demos and cartridges rebuild identical (docs/TESTED_SOFTWARE.md). Not modelled: the boot ROM itself (a loader that ends in it, such as loader.lnx, comes back as data), headerless `.lyx` files and the second cartridge bank.
- The Game Boy Advance lane (ARM7TDMI): `info` and `reach` take a `.gba` cartridge; the program comes back as GNU as source (`.syntax unified`, `.arm` and `.thumb` where the processor changes state, literal pools under labels, the header field by field, hardware registers by libgba name) that CodeBreaker's own ARM/Thumb assembler builds back into the same ROM, byte for byte, and its functions are judged in CodeBreaker's own ARM7TDMI interpreter (both states, banked registers, the console's memory map, the BIOS calls logged). Open-source GBA test ROMs and homebrew rebuild identical (docs/TESTED_SOFTWARE.md).
- The PlayStation lane (MIPS R3000A): `info` and `reach` take a PS-X EXE; the program comes back as GNU as source (every function, the
  header field by field, strings, tables and hardware registers by name) that CodeBreaker's own MIPS assembler builds back into the
  same executable, byte for byte, and its functions are judged in CodeBreaker's own R3000A interpreter (delay slots, the BIOS calls,
  the GTE's registers and its commands that need no division). 58 open-source PS1 programs rebuild identical (docs/TESTED_SOFTWARE.md).

### Fixed
- A fresh clone builds and passes the gate: `tools\build_native.cmd` builds every engine the program calls (the
  decompiler, XEX and NASM included); tests that need copyrighted or out-of-repo inputs find them in
  `binaries/test-inputs/` or in checkouts beside this one, and are skipped where those are absent.
- `dos-build` and `driver-build` write a link script that names the program relative to its folder, so a build
  leaves the source folder the same on every machine.
- `tidy-state` knows the `origin`, `oss` and `setup` folders as CodeBreaker's own.

### Changed
- A platform lane is one plug-in (roadmap track 6): its registration object (`register_lane({...})` in the lane's own `engine/machine_<name>.cpp`: name, platform
  descriptor, probe, machine spec, the `info` text, the extensions `reach` takes) is named once in `engine/lane_list.cpp`, and the places that listed lanes by hand -- the
  platform enum and its probes, `reach`'s probes and extensions, `info`'s detection blocks, the lane kit's chains and name lists, the tests' counts and name lists --
  iterate the registry instead. All 45 console and home-computer lanes moved; `codebreaker info` and `reach` say what they said. `docs/LANES.md` section 5 is the new
  checklist. A lane written against the old enum (`Id::<Name>`, `Probes::is_<name>`, a `case` in `Registry::recognises`) uses `MachineSpec::name` and `register_lane` instead.
- Console-lane source writers are much faster (roadmap track 5): the ARM, MIPS and 68000 assemblers no longer copy the whole label table for every forward reference (PSP DOSBox EBOOT.PBP 185 s -> 3.4 s, 3DS Universal-Updater 102 s -> 3.2 s, Wii U SuDokuL 528 s -> 5.5 s), the Switch writer's search for uncalled functions no longer re-walks found code (NX-Shell 44 s -> 10 s), and `CB_PROFILE=1` times the 3DS, Switch and MIPS writers' stages. Rebuilt files and `reach --judge` tables are byte-identical; numbers in docs/SPEED.md.
- CodeBreaker builds with any modern compiler on Windows: MSVC 2022 and 2026, Clang (clang-cl) and GCC (MinGW-w64).
  Compiler flags are chosen per compiler, Windows libraries are linked by name, MSVC-only intrinsics and CRT calls
  have portable forms, and CI builds and tests with all three compilers.
- Builds need no Python: the engines take Capstone's and Unicorn's headers from `native/third_party/include`.
- Python-era design notes moved to `docs/history/`; the current docs give `codebreaker <command>` and the native
  source paths.

## 1.0.0 — 2026-11-14

The first official release: CodeBreaker as one native C++20 program.

- Every command (75) runs in `codebreaker.exe`; the only Python left is the terminal interface (`codebreaker ui`).
- Lanes: 32- and 16-bit Windows (C, or assembly where it was written in assembly), VxD drivers and DOS programs
  (whole-file assembly, rebuilt byte for byte), Xbox 360 (C per function, or whole titles recompiled to C++), XNA
  (C#, content, HLSL), Java (C++03), NES / Master System / Game Gear / Game Boy / Genesis / ZX Spectrum / MSX
  (assembly source), and the universal translator (Java, Python, C# to C / C++17 / C++03).
- Proven: `tools\gate.cmd` (5,450 unit tests, 155 command cases, the interface's tests); `codebreaker regress`
  all15 2/2, setup 2/2, install 2/2 (Windows 95 to the desktop on 22 rebuilt modules), slow (Minecraft Xbox 360
  Edition recompiled and run headless).
- Release package `CodeBreaker-1.0.0-win64.zip`: the program, its engines and data, no tests.
